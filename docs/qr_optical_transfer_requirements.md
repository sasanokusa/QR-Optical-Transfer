# QR Optical Transfer Web 要件定義 v0.1

## 1. 目的

ネットワーク、USBメモリ、Bluetooth等を使わず、**送信側画面に連続表示されるQRコードを、受信側カメラで読み取ることでファイルまたはテキストデータを転送するWebアプリケーション**を作る。

初期MVPでは、

- **Windows PC = センダー**
- **Mac = レシーバー**

とし、MacのカメラでWindows画面上のQRを読み取る構成にする。

---

## 2. 前提条件

| 項目 | 内容 |
|---|---|
| 通信方向 | センダー → レシーバーの片方向のみ |
| ACK / 再送要求 | なし |
| 転送媒体 | 画面に表示したQRコード |
| 受信媒体 | カメラ |
| 実装形態 | Webアプリ |
| 初期環境 | 送信側Windows、受信側Mac |
| 主用途 | 小〜中容量ファイル、テキスト、設定ファイル、鍵ファイル、スクリプト等の転送実験 |
| 想定しないもの | 高速転送、大容量動画転送、双方向通信、完全な信頼性保証 |

Webでカメラを使う場合、`getUserMedia()` の制約により、受信側アプリは基本的に以下のいずれかで動かす必要がある。

- HTTPS
- localhost
- ブラウザが許可する安全なローカル環境

---

## 3. 基本フロー

### 3.1 センダー側

1. ユーザーが送信したいファイルを選択する。
2. アプリがファイルを読み込む。
3. 必要なら圧縮する。
4. 必要なら暗号化する。
5. 転送用メタデータを生成する。
6. 最初に**マニフェストQR**を表示する。
7. レシーバー側の準備ができたら、人間が送信開始ボタンを押す。
8. データ本体をチャンク分割し、QRコードとして連続表示する。
9. 全チャンク表示後も、一定回数または手動停止までループ表示する。

### 3.2 レシーバー側

1. カメラを起動する。
2. 最初のマニフェストQRを読み取る。
3. ファイル名、サイズ、チャンク数、暗号化有無などを表示する。
4. ユーザーが受信を承認する。
5. 連続表示されるデータQRを読み取る。
6. チャンク番号ごとに保存する。
7. 重複チャンクは破棄する。
8. 全チャンクが揃ったら結合する。
9. ハッシュ検証を行う。
10. 必要なら復号・展開する。
11. ファイルとして保存できるようにする。

---

## 4. 重要な設計方針

### 4.1 最初のQRは「鍵」ではなく「転送情報」にする

マニフェストQRには、ファイル転送に必要なメタデータを入れる。

ただし、暗号化を行う場合、復号パスワードや復号キーそのものをマニフェストQRに含めるべきではない。

同じ可視チャネルで暗号化データと復号キーを両方送ると、第三者が画面を録画した場合に復号できてしまうため。

### 4.2 マニフェストQRに含める情報

| 情報 | マニフェストQRに入れるか |
|---|---|
| ファイル名 | 入れる |
| MIME type | 入れる |
| 元サイズ | 入れる |
| 圧縮方式 | 入れる |
| 暗号化方式 | 入れる |
| salt / iv / KDF設定 | 入れる |
| 復号パスワード | 入れない |
| ファイル全体SHA-256 | 入れる |

暗号化する場合は、レシーバー側で人間がパスフレーズを入力する方式を標準とする。

## 5. QR転送プロトコル案

### 5.1 マニフェストQR

最初のQRはJSON形式とする。

```json
{
  "proto": "QROPT/1",
  "type": "manifest",
  "transferId": "8f4c2a9d7b1e",
  "file": {
    "name": "sample.zip",
    "mime": "application/zip",
    "size": 1234567
  },
  "payload": {
    "encoding": "base64url",
    "compression": "gzip",
    "encryption": "none",
    "chunkSize": 900,
    "chunkCount": 1372
  },
  "hash": {
    "alg": "SHA-256",
    "value": "..."
  },
  "display": {
    "fps": 5,
    "loop": true
  }
}
```

### 5.2 データQR

各QRには、必ずチャンク番号を含める。

```json
{
  "proto": "QROPT/1",
  "type": "chunk",
  "transferId": "8f4c2a9d7b1e",
  "seq": 42,
  "total": 1372,
  "data": "base64url..."
}
```

MVPではJSONで十分とする。

速度や容量効率を上げたい場合は、将来的に以下を検討する。

- CBOR
- MessagePack
- 独自バイナリ形式
- QR内データのヘッダ短縮

## 6. 機能要件

### 6.1 センダー機能

| ID | 要件 |
|---|---|
| S-01 | ファイルをドラッグ＆ドロップまたはファイル選択で取り込める |
| S-02 | ファイル名、サイズ、MIME typeを取得できる |
| S-03 | SHA-256ハッシュを計算できる |
| S-04 | 任意でgzip圧縮できる |
| S-05 | 任意でパスフレーズ暗号化できる |
| S-06 | マニフェストQRを生成できる |
| S-07 | データを指定サイズでチャンク分割できる |
| S-08 | QRを指定FPSで連続表示できる |
| S-09 | 一時停止、再開、停止ができる |
| S-10 | チャンク表示速度を変更できる |
| S-11 | 全チャンク表示後にループできる |
| S-12 | 現在の表示チャンク番号と進捗を表示できる |

### 6.2 レシーバー機能

| ID | 要件 |
|---|---|
| R-01 | カメラを起動できる |
| R-02 | カメラ映像からQRコードを検出できる |
| R-03 | マニフェストQRを認識できる |
| R-04 | ファイル情報を表示し、受信開始を確認できる |
| R-05 | データQRを連続読み取りできる |
| R-06 | transferIdが一致しないQRを無視できる |
| R-07 | seq番号でチャンクを管理できる |
| R-08 | 重複チャンクを破棄できる |
| R-09 | 未受信チャンク数を表示できる |
| R-10 | 全チャンク受信後に結合できる |
| R-11 | SHA-256で整合性検証できる |
| R-12 | 必要なら復号できる |
| R-13 | 必要なら展開できる |
| R-14 | 完成ファイルをダウンロードできる |

## 7. 非機能要件

| 分類 | 要件 |
|---|---|
| 互換性 | Chrome / Edge / Safari のうち、最低でもMac ChromeまたはSafariで受信できる |
| オフライン性 | アプリ本体は事前に読み込むか、PWA化してキャッシュ可能にする |
| 転送速度 | MVP目標は 2〜10 KB/s 程度 |
| ファイルサイズ | MVPでは 1〜5 MB 程度までを現実的な対象にする |
| 信頼性 | 全チャンクが揃うまでセンダーはループ表示する |
| 安全性 | 復号キーはQRに含めない設計を標準にする |
| 操作性 | 送信開始は人間が押す。自動同期はしない |
| 視認性 | QRは画面中央に大きく表示し、背景は白、QRは黒を基本にする |

## 8. エラー訂正・欠損対策

双方向通信をしない場合、レシーバーからセンダーに対して「特定チャンクの再送」を要求できない。

そのため、MVPでは以下の方式を採用する。

### 8.1 MVP方式

**全チャンクを何周もループ表示する。**

レシーバーは読めたチャンクを蓄積し、欠けている番号だけ次周以降で埋める。

### 8.2 将来方式

| 方式 | 内容 |
|---|---|
| インターリーブ | `0,1,2...`ではなく順番を散らして表示する |
| パリティチャンク | XORなどで簡易復元用チャンクを追加する |
| Fountain code | どのQRを読んでも一定数集まれば復元できる方式 |
| 複数QR同時表示 | 画面に2〜4個のQRを並べてカメラで同時取得する |

## 9. MVP仕様案

| 項目 | MVP仕様 |
|---|---|
| 転送対象 | 単一ファイル |
| 最大サイズ | 5 MB目安 |
| 圧縮 | gzip、任意 |
| 暗号化 | なし、またはAES-GCM + 手入力パスフレーズ |
| QRデータ形式 | JSON + base64url |
| 1QRあたり実データ | 600〜1000 bytes程度から調整 |
| FPS | 3 / 5 / 8 / 10 を選択式 |
| 再送方式 | 全チャンクループ |
| 受信方式 | seq番号で重複排除 |
| 検証 | SHA-256 |
| UI | Sender / Receiver の2モード切替 |

## 14. 最初の実装ゴール

最初の実装ゴールは以下とする。

> Windowsのブラウザで「Hello Worldを100個のチャンクにしたQR」を5fpsで表示し、Macのブラウザでカメラ読み取りして、100個全部揃ったら元テキストを復元する。

この実験が成功したら、次に以下を追加する。

1. ファイルBlob化
2. ハッシュ検証
3. ループ再送
4. 圧縮
5. 暗号化
6. PWA化

## 15. 初期リスク

| リスク | 内容 | 対策 |
|---|---|---|
| QRが読めない | FPSが高すぎる、QRが小さい、画面反射、カメラ性能不足 | FPSを下げる、QRを大きくする、輝度を上げる |
| 欠損が多い | カメラのピントや露出が安定しない | チャンクループ、受信済み管理、誤り訂正レベル調整 |
| 転送が遅い | QR容量とFPSに限界がある | 圧縮、チャンクサイズ調整、複数QR表示を検討 |
| JSONオーバーヘッドが大きい | 各チャンクにメタデータが多い | 将来的に短縮ヘッダまたはバイナリ化 |
| 暗号化の扱いが危険 | 鍵をQRに含めると意味が薄い | 復号パスフレーズは別経路または手入力 |

---

## 16. 備考

このアプリは、実用的な高速ファイル転送というより、以下に近い性質を持つ。

- エアギャップ環境向けの実験的転送
- 物理可視チャネルによる片方向通信
- QRを使った簡易データダイオード
- ネットワークを信用しない環境での低速ファイル搬送

そのため、初期段階では速度よりも以下を優先する。

1. 確実に復元できること
2. 欠損チャンクを可視化できること
3. 操作が単純であること
4. プロトコルが読みやすくデバッグしやすいこと
